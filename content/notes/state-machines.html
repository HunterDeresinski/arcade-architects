#What it is

A formal architecture where every behaviour — Idle, Walk, Jump, Attack, Hurt — is its own node with its own script, and a manager node hands control between them. Godot also ships AnimationTree with a built-in state machine for blending animations.

It's the standard way large games structure characters, and it's genuinely good engineering.

#Why not this week

You already have a state machine. The enum + match pattern in Enemy States is one — it just doesn't have a folder of files around it.

The formal version pays off when you have a dozen states, several characters sharing behaviour, and months to maintain it. In five days it costs you a day of setup and buys nothing a match statement doesn't already do. Teams that go down this road on Wednesday are still debugging their state manager on Friday instead of making levels.

AnimationTree is worse for camp purposes: the blend-space UI is genuinely confusing, and students find it in the docs and assume it's required. It isn't.

#If a student really wants it

They probably don't need talking out of it so much as timing advice: this is a great first project after camp, when they have a game that already works and want to refactor it.

Point them at:

  • Godot docs → AnimationTree and StateMachine guides
  • The community "Finite State Machine" tutorials — search godot 4 state machine node
  • Their own Enemy States enemy as the thing to refactor. Refactoring code you wrote and understand is the best possible way to learn an architecture pattern.

#What to say in the moment

"You already built a state machine — the match block is the machine. The fancier version splits it into files, which helps when you have twenty states. You have four. Build the game this week; refactor it in July if you still want to."
