Your game will break. Every game breaks, every day, for every developer in the world. Debugging isn't the punishment for coding badly — it is coding. This note is where you come when something doesn't work.

❗The one rule

Read the error message. Godot almost always tells you what's wrong and which line it's on. Most of camp's "help me, it's broken" moments are solved by scrolling down and actually reading the red text.

#Where the debug window is

Everything lives in the bottom panel of the editor (Godot Editor Tour). If you don't see it, press F5 to run your game — it opens automatically. You can also click the tab names along the very bottom of the window.

TabWhat it shows
OutputYour print() messages, plus errors in red and warnings in yellow. This is the one you'll use 90% of the time.
DebuggerDetailed crash info: the error, the line number, and the stack trace (the path your code took to get there).
Debugger → ErrorsA running list of every error and warning. Click one to jump to the code.
Debugger → Stack TraceShows which function called which function. Read it top to bottom.
Debugger → Misc / MonitorsPerformance graphs — FPS, memory. Not needed at camp, but neat.
💡Turn on "Auto Switch to Remote Scene Tree"

While the game is running, the Scene dock has a Remote button at the top. Click it and you see the live node tree of the running game — real positions, real values, updating in real time. This is the fastest way to answer "is my bullet even being created?" and "where did my player actually go?"

Clear the Output before each run (the 🚫 icon in the Output panel). Otherwise old messages pile up and you'll chase a bug you already fixed.

#Print statements — your best tool

print() writes a message to the Output panel. That's it. That's the whole feature, and it's the tool professional developers reach for first.

func _ready():
	print("Player is ready!")

func take_damage(amount):
	print("Took damage: ", amount, " — health is now ", health)

#What to print

The goal is to answer one of three questions:

  1. Did this code run at all? → Put print("here") inside the function. If nothing shows up, the function is never being called. That's your bug.
  2. What is this value right now? → print("speed = ", speed) Label it! print(speed) alone becomes a mystery number once you have five prints going.
  3. How many times did this happen? → If you expected one bullet and Output shows ten print("shot!") lines, you found your problem.

#Print tricks

print("=== ENEMY DIED ===")        # loud markers are easy to spot
print("pos: ", global_position)    # Vector2 prints fine
print(velocity, " | ", is_on_floor())  # multiple values, one line

print_debug("only in the editor")  # includes the file + line automatically
push_warning("this looks wrong")   # shows as a yellow warning
push_error("this is bad")          # shows as a red error
⚠️Don't print inside _process() forever

_process() runs ~60 times a second, so you'll flood the Output with thousands of lines and the editor will crawl. Print there only while you're actively hunting something, then delete it.

Clean up your prints before the Friday showcase. Leftover print("aaaaa") is funny until a judge sees it.

#Reading an error message

A Godot error looks like this:

res://player.gd:24 - Invalid access to property or key 'position'
on a base object of type 'Nil'.

Break it into three parts:

  • res://player.gd — which file
  • :24 — which line (click the error to jump straight there)
  • the rest — what went wrong

Nine times out of ten the fix is on that exact line or the line right above it.

These are the hard ones. No error message means Godot did exactly what you asked; you asked for the wrong thing.

💡The yellow triangle

A ⚠ next to a node in the Scene dock is Godot telling you the node is misconfigured before you even run. Hover it and read the message. It's usually "this CollisionShape2D has no shape."

#The thought process

When something breaks, don't randomly change things. Work the loop:

1. Reproduce it. What exactly do you do to make it happen? "It breaks sometimes" is unfixable. "It breaks when I jump into the left wall" is fixable.

2. Read the error. File, line, message. Click it to jump there.

3. Guess out loud. Say what you think is happening: "I think the bullet is spawning but at position zero." A guess you can test beats staring at code.

4. Test the guess with one print. print(bullet.global_position). You either confirm it or eliminate it. Both are progress.

5. Narrow it down. Cut the problem in half. Is the function even running? → yes. Is the value right when it enters? → yes. Is it right when it leaves? → no. Now you know exactly where to look.

6. Change ONE thing. Then run. If you change four things and it works, you don't know why, and it'll break again tomorrow.

7. When it works, understand why. If you can't explain the fix, you didn't fix it — you moved it.

❗The 15-minute rule

Stuck on the same bug for 15 minutes with no new information? Stop and ask. You're not failing — you've run out of things you can test alone. Bring your best guess with you: "I think the signal isn't connected, but I checked and it looks fine." That gets you a much faster answer than "it's broken."

#Rubber ducking

Explain the broken code, out loud, line by line, to a teammate — or to a stuffed animal, or to the wall. Say what each line is supposed to do. You will very often catch the bug mid-sentence, before anyone answers you. This is a real technique with a silly name, and it works.

#Breakpoints (the fancy way)

When prints aren't enough, click in the margin to the left of a line number in the Script editor. A red dot appears. Run the game — it will freeze the instant it reaches that line.

While it's paused:

  • The Debugger → Stack Trace panel shows every local variable and its current value. No prints needed.
  • Step Into (F11) — run one line at a time
  • Continue (F7) — resume until the next breakpoint
  • Press Stop (F8) when you're done

You can also write breakpoint as a line in your code to do the same thing.

Breakpoints are the grown-up version of print(). Try one on Day 4 when you're chasing something stubborn.

#Before you ask for help

Run this checklist first. It resolves most bugs on its own:

  • Did I save the scene and the script? (Ctrl+S)
  • Did I read the actual error text in the Output panel?
  • Did I click the error to see which line?
  • Is the script attached to the node I think it is?
  • Do my $NodeName paths match the Scene dock exactly — spelling and capitals?
  • Is the signal connected (green 🔌 icon in the Node dock)?
  • Are there any yellow ⚠ warnings on my nodes?
  • Did I add a print() to confirm the code is even running?

Then bring: what you expected, what actually happened, and what you already tried.

💡Copy the error, search the error

Pasting a Godot error into a search engine, minus your own file names, finds someone who hit the same thing. Every developer does this constantly. It's not cheating — it's the job.
