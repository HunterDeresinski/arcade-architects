Difficulty: ⭐⭐⭐⭐ hard · Camp verdict: ❌ don't · Do instead: High Scores That Persist

#What it is

Saving the whole game state — where the player is standing, which enemies are dead, which chests are open, inventory contents, quest progress — and restoring it exactly on load. Save slots, autosaves, "continue where you left off."

#Why not this week

The file writing is easy — High Scores That Persist shows the whole technique in about fifteen lines, and it's the same FileAccess and JSON either way.

The hard part isn't saving. It's deciding what counts as "the state of the game." Every object needs to describe itself as data and rebuild itself from that data. Every new feature added on Thursday needs a save/load path too, or loading silently breaks. It's an architectural commitment made on day one, and camp games are built by improvisation — which is the correct way to build them in five days.

There's also no need. A tiny game is 3–10 minutes long. Nobody needs to save halfway through, and a save system solves a problem your game doesn't have.

#What to build instead

The wantThe five-minute version
"I want progress to persist"High Scores That Persist — a high score is progress
"I want to unlock levels"Save one number, levels_unlocked, in your Autoload and Global
"I want to keep my settings"Same file, a dictionary with volume and difficulty
"I want to continue where I left off"Save the level number only, and restart that level from the beginning

That last row is the good compromise. Saving "you were on level 4" is 95% of the feeling of a save system for 5% of the work, and plenty of real arcade and mobile games do exactly that.

# in your Global autoload
func save_progress():
	var f = FileAccess.open("user://progress.json", FileAccess.WRITE)
	f.store_string(JSON.stringify({
		"level": current_level,
		"levels_unlocked": levels_unlocked,
		"high_score": high_score,
		"music_volume": music_volume,
	}))
	f.close()

Genuinely, that's enough for almost any small game.

#If someone goes further after camp

The standard Godot approach: give every saveable node a save() method returning a dictionary and a load(data) method that restores it, put them all in a persist group, and iterate.

  • Godot docs → Saving games
  • Look up godot 4 save system resource for the Resource-based approach, which is cleaner
  • Warn them about store_var with objects — it can execute arbitrary code on load and is a real security issue in a shared game. JSON is safer.

#What to say in the moment

"Writing the file is easy — you already know how from the high score note. The hard part is describing your whole game as data, and that's a design decision you'd have to make before you started building. How about we save which level you reached? That's most of the feeling, and it's ten minutes."
